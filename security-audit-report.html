HIGH #01 privilege-escalation

reset-enrollment-code lacks tier guard → onboarding-hijack takeover of higher-privileged (admin) accounts

apps/api/src/routes/users.ts:292
Exploit

POST /users/:id/reset-enrollment-code is gated ONLY by can('manage_users') || can('set_pins') (line 292) with NO canActOnTarget tier check — unlike PATCH /users/:id (line 179) and create (canAssignRole). A tier-3 office_manager or hr_manager (both have manage_users AND set_pins in ROLE_DEFAULTS, permissions.ts tier3) can call this against ANY user whose pin_hash IS NULL. GET /auth/roster is public and returns each user's id, role, and pin_set flag, so the attacker can pick a franchise_manager/full_admin (tier 4 / apex) who was just created or PIN-reset and hasn't onboarded (pin_set=0). The handler passes the 409 pin_hash check, reissues a code, and RETURNS the plaintext { code } in the HTTP response (line 324). The attacker then calls POST /auth/set-pin with { user_id: <adminId>, pin: <attacker-chosen>, enrollment_code: <returned code> } (auth.ts) which succeeds because pin_set is false and the code matches — setting the admin's PIN. The attacker signs in via /auth/token as that full_admin, gaining apex (tier-5) privileges: manage_roles_permissions, system_settings, everything. Full account takeover of a superior account by a subordinate.

Fix

Resolve the target's role and enforce the same tier guard used by PATCH: fetch target role and require canActOnTarget(callerRole, targetRole) before reissuing/returning the enrollment code. Fail closed on unknown target role. (Optionally also require canActOnTarget in /auth/set-pin is not possible since it is unauthenticated — the fix belongs at code issuance.)

HIGH #02 broken-access-control

Any authenticated user can join any conversation via a crafted conversation_participants INSERT, then read private messages and post

apps/api/src/routes/sync.ts:752
Exploit

A low-privilege user (e.g. role 'crew') crafts a /sync/push outbox entry {operation:'INSERT', table_name:'conversation_participants', payload:{conversation_id:'<victim DM/group id>', user_id:'<attacker id>', notify_pref:'regular'}}. In the push loop conversation_participants is not in PRIVILEGED_TABLE_PERM, not DELETE_FORBIDDEN, and requiredOperationPerm returns null (syncPolicy.ts:228 maps INSERT/UPDATE/DELETE -> null = allowed to any authed user). No membership/ownership guard exists for this table (only `messages` INSERT is gated on membership at sync.ts:752). applyWritePolicy keeps user_id verbatim (not in SENSITIVE_DENY or ATTRIBUTION_COLUMNS for conversation_participants), so the row inserts on ON CONFLICT (conversation_id,user_id). The attacker is now a participant. On the next /sync/pull, chatScopeSql (sync.ts:85-93) scopes messages/conversations to `conversation_id IN (SELECT ... WHERE user_id = caller)` — which now includes the victim conversation — so the attacker downloads every message/participant of a conversation between other users. Being a participant also passes the messages-INSERT membership check (sync.ts:754-765), letting the attacker post into that private conversation. The client's addParticipant() (apps/mobile/src/db/queries/chat.ts:299) emits exactly this outbox shape, confirming the server is the only authorization point and it enforces nothing. Conversation ids are learnable (org-wide notifications/push payloads carry conversationId, and conversations pull is only scoped, not secret to enumeration via retries).

Fix

In the push handler, add an explicit authorization branch for conversation_participants writes (INSERT/UPDATE/DELETE): require that the caller is already a participant of payload.conversation_id (or the conversation's created_by / a manage_teams holder) before allowing the write, mirroring the messages membership check. For self-join specifically, disallow adding a user_id other than an already-authorized member; do not let an arbitrary caller add themselves to a conversation they don't belong to.

HIGH #03 dos-memory-growth

Unauthenticated memory-exhaustion DoS via /auth/token: arbitrary user_id values create permanent, unbounded entries in the in-memory `attempts` map (no IP limit, no maxLength, no eviction)

apps/api/src/routes/auth.ts:147
Exploit

POST /auth/token is public and is explicitly skipped by the global `mut:` rate limiter (index.ts line 101: `if (request.url.startsWith('/auth')) return`). Its only guard is the per-user_id lockout `isLocked('token:'+user_id)`. For an unknown user_id, `isLocked` is false, so the handler runs a DB SELECT and then hits `if (!user) { recordFail(lockKey); ... }` (auth.ts:146-147), which does `attempts.set('token:'+user_id, ...)` for a brand-new key. That key is never evicted: recordSuccess only deletes on a *valid* login, and the window-expiry path (auth.ts:44-49) overwrites the value but keeps the key. The body schema for user_id is `{ type: 'string' }` with NO maxLength (auth.ts:118), so each key can be up to the 1 MiB body limit. An unauthenticated attacker loops POST /auth/token with random/large user_id strings; every request permanently adds one (potentially ~1 MB) entry to the shared `attempts` Map (and one DB round-trip). Because the API runs as a single container (see rateLimit.ts comment) with no map sweeper, the process grows until OOM and the whole API dies for all users. The same unbounded-key/no-eviction defect applies to the `buckets` Map in lib/rateLimit.ts (rateLimit.ts:4) — nothing ever removes entries.

Fix

Add a per-IP rate limit on /auth/token (and /set-pin) before touching the map/DB; add `maxLength` (e.g. 64) to the user_id schema; and cap the size of `attempts`/`buckets` (LRU or periodic sweep of expired entries). Do not create an `attempts` entry for a non-existent user, or key the unknown-user failure counter by IP rather than by attacker-supplied user_id.

MEDIUM #04 session-management

Refresh token is accepted as an access token (no type/audience separation) → 7-day bearer that bypasses the 15m expiry and active/expiry recheck

apps/api/src/index.ts:89
Exploit

The refresh token is a plain JWT signed with the SAME secret and carries { sub, type:'refresh' } with expiresIn 7d (auth.ts lines 179-180, 272). The authenticate decorator (index.ts line 88-90) only calls request.jwtVerify() — it never checks a token type/audience — and every protected route authorizes off request.user.sub with role/permissions re-resolved from the DB (sync.ts resolveCaller, permissions.requirePermission), which do NOT need the role claim. Consequently a refresh token presented as `Authorization: Bearer <refresh>` verifies successfully and is treated as a fully-authenticated session for 7 days, defeating the intentional 15-minute access-token lifetime. Worse: /auth/refresh (auth.ts line 300+) re-checks user.active and expires_at before minting a new JWT, but resolveCaller/requirePermission on the data routes do NOT — so a user who is deactivated (active=false) or whose expires_at has passed keeps full read/write access by directly using their still-valid refresh token as a bearer until it expires 7 days later, with no way to revoke it (stateless JWT, no rotation).

Fix

Give refresh tokens a distinct audience/type and reject them in the authenticate decorator (verify the access token carries no type:'refresh', or sign refresh tokens with a separate secret/aud and only accept that aud at /auth/refresh). Additionally, re-check users.active and expires_at in resolveCaller/requirePermission so a deactivated/expired user is cut off within the token window, not just at refresh time.

MEDIUM #05 privilege-escalation

Sync users-INSERT path skips the role-assignment/tier guard for new rows, letting a franchise_manager mint a full_admin (apex) account

apps/api/src/routes/sync.ts:678
Exploit

The users write guards in /sync/push (target-role guard, canActOnTarget, and the canAssignRole role-assignment check at line 700) are all nested inside `if (target)` (line 678), where `target` is the pre-existing row fetched by `SELECT role,active FROM users WHERE id=$1`. For a brand-new UUID the row doesn't exist, so `target` is undefined and the whole block is skipped. A tier-4 franchise_manager holds manage_users (passes PRIVILEGED_TABLE_PERM) and manage_roles_permissions, so applyWritePolicy uses deny=USERS_ALWAYS_DENY only and lets `role` and `permission_overrides` through. They push a users INSERT entry with a fresh id and role:'full_admin'. Because pin_hash was made nullable in migration 003, the row inserts successfully (active defaults TRUE, pin_set FALSE), creating an apex full_admin. This is precisely the action REST POST /users blocks via canAssignRole(creatorRole,role) (users.ts:103) and that the codified invariant canAssignRole('franchise_manager','full_admin')===false (permissions.test.ts:95) forbids. The equivalent UPDATE on an existing full_admin is correctly blocked (target defined -> canActOnTarget(franchise_manager,full_admin)=false), so only the new-row INSERT is the hole. Impact is bounded: pin_hash and enrollment_code_hash cannot be set via sync (USERS_ALWAYS_DENY), so the minted admin is dormant/non-loginable via the sync path (auth set-pin at auth.ts:253 requires enrollment_code_hash), and the attacker can't UPDATE it afterward (now guarded). Concrete impact is therefore the authorization-control/apex-invariant bypass, users-roster pollution with bogus admin rows, and inflation of the active-full_admin count (each defeats the 'last active full_admin' deactivation check), rather than immediate apex login.

Fix

Move the role-assignment authorization out of the `if (target)` block so it runs for new-user INSERTs too: unconditionally validate `entry.payload.role` with canAssignRole(caller.role, role) (and, mirroring REST users.ts:109, require manage_roles_permissions when creating a PRIVILEGED_ROLES role or any permission_overrides) whenever a users INSERT/UPDATE carries a role — regardless of whether the target row currently exists. Keep the existing target-row guards for the update case.

MEDIUM #06 broken-access-control

Missing write authorization on conversation_participants lets any user join/read/kick arbitrary conversations

apps/api/src/routes/sync.ts:752
Exploit

conversation_participants is in ALLOWED_TABLES and its op-perms are all null (syncPolicy.ts:228 -> requiredOperationPerm returns null = 'any authed user'). It is NOT in ATTRIBUTION_COLUMNS or SENSITIVE_DENY, so applyWritePolicy (syncPolicy.ts:146) keeps the client-supplied user_id verbatim; keepRealColumns only strips non-columns. The push loop guards messages INSERT against membership (sync.ts:752-766) but has NO equivalent guard for conversation_participants. Exploit A (silent kick / integrity): any authenticated user (e.g. lowest 'crew' role) who is a member of a group conversation posts an outbox entry {operation:'DELETE', table_name:'conversation_participants', payload:{conversation_id:<known conv id>, user_id:<victim id>}}. keyColumns = 'conversation_id, user_id' (CONFLICT_TARGETS), so applyEntry runs DELETE FROM conversation_participants WHERE conversation_id=$1 AND user_id=$2 (sync.ts:207-210) -> victim (including the conversation creator) is silently removed. Victim user_ids are broadly known because the entire users table is fully synced to every device. Exploit B (unauthorized read): {operation:'INSERT', conversation_participants, {conversation_id:<target>, user_id:<self>}} upserts the attacker in as a participant (ON CONFLICT DO UPDATE); the subsequent /sync/pull chatScopeSql then returns that conversation's messages+participants and the messages membership guard now passes, letting the attacker read and post. (Read is bounded by needing the target conversation UUID -- reliable for a previously-removed member who retains the id, or any leaked id -- but the kick/add in Exploit A works with certainty among co-members.)

Fix

Authorize conversation_participants writes like messages: for INSERT/UPDATE/DELETE require the caller to already be a participant (or creator) of the target conversation_id, and for self-join force user_id to the caller. Add conversation_participants membership checks in the sync.ts push loop mirroring the messages block, and consider adding conversations.created_by ownership checks on conversations UPDATE (also op-perm null today).

MEDIUM #07 broken-access-control

messages UPDATE is not gated on membership or sender ownership — any user can edit another user's message body

apps/api/src/routes/sync.ts:752
Exploit

The membership guard at sync.ts:752 only runs for `messages` with operation==='INSERT'. requiredOperationPerm('messages','UPDATE') is null (syncPolicy.ts:229), so a messages UPDATE reaches applyEntry with no membership or ownership check. applyWritePolicy for UPDATE deletes sender_id (attribution) but keeps `body`/`urgency`, and the generated UPDATE is keyed on id alone with no `sender_id = caller` or conversation-membership constraint. A user who knows a message id (e.g. any participant of a group chat, or the attacker from the join exploit above) can push {operation:'UPDATE', table_name:'messages', payload:{id:'<other user's message id>', body:'forged text'}} and silently rewrite another user's message content, which then propagates to all participants on pull. No audit trail distinguishes the tamper since sender_id is unchanged.

Fix

Gate messages UPDATE the same way as INSERT: verify the caller participates in the message's conversation AND owns the row (messages.sender_id = caller) before allowing the write; otherwise reject. Consider disallowing message edits entirely via sync if not a product requirement.

MEDIUM #08 dos-unbounded-payload

/sync/push `entries` array has no maxItems bound (telemetry caps at 100) — a single authenticated request drives thousands of sequential privileged DB writes

apps/api/src/routes/sync.ts:546
Exploit

The push body schema is `entries: { type: 'array', items: { type: 'object' } }` (sync.ts:546) with no maxItems — contrast telemetry.ts:19 which deliberately sets `maxItems: 100`. The handler then iterates every entry (sync.ts `for (const entry of entries)`), doing per-entry permission resolution and INSERT/UPDATE/DELETE/ADJUST DB work, plus fire-and-forget push notifications for message rows. No custom Fastify `bodyLimit` is configured, so only the 1 MiB default caps the payload — roughly 15–20k minimal entry objects per request. The endpoint is gated only by the generous `mut:` bucket (overRateLimit = 120 requests/min/user, index.ts:108), so one authenticated crew device can submit ~120 × ~20k = millions of serialized DB writes per minute on the single-container API/DB, monopolizing the connection and starving all other users. The explicit maxItems on the far-cheaper telemetry path shows a bound was intended here too.

Fix

Add `maxItems` (e.g. 500–1000) to the entries array schema to match the telemetry pattern, and reject oversized batches with 413/400 before the loop.

MEDIUM #09 client-hardening/threat-model-gap

At-rest snapshot encryption provides no protection against the XSS threat its own comments claim to defend against (key lives in XSS-readable sessionStorage)

apps/mobile/src/db/webCrypto.ts:126
Exploit

webPersistence.ts:4-8 and webCrypto.ts:5-14 explicitly assert that AES-GCM encrypting the sql.js snapshot means 'a shared/compromised browser or an XSS read of IndexedDB yields ciphertext, not the full dataset.' But the AES-256 key is exported raw and written to sessionStorage under 'ip-web-dbkey' (webCrypto.ts:126) and the modules are already loaded in the page. Any XSS executing on invenpro.app can do: JSON key = atob(sessionStorage['ip-web-dbkey']) -> importKey -> read the IndexedDB 'sqlite-snapshot' blob (strip 4-byte MAGIC) -> decryptBytes, recovering the entire local inventory/user dataset in plaintext. Even simpler, XSS can call the exported getSnapshotKey()/loadDbSnapshot() directly. sessionStorage is same-origin JS-readable, exactly like IndexedDB, so moving the key there buys nothing against a script-execution attacker. The encryption only helps against offline filesystem access to the LevelDB files by a process with NO JS context on the origin; the prominent 'XSS' claim in the comments is false and gives false assurance.

Fix

Correct the comments to scope the control to offline/at-rest disk access only, and stop advertising XSS resistance. Real XSS mitigation must come from the CSP/script-src lockdown, not from co-locating key+ciphertext in the same origin's JS-reachable storage. If protection against a live-page attacker is a goal, the key cannot be derivable by page script (e.g. non-extractable key held only in a worker with no message API to export it), which the current design does not achieve.

MEDIUM #10 client-hardening/ineffective-control

Web idle auto-wipe leaves the live in-memory DB and React session intact, and the persistence flush regenerates the key — a walked-away browser is not actually protected

apps/mobile/src/auth/session.web.ts:176
Exploit

The stated goal (useWebIdleWipe.ts:1-8, session.web.ts:161-176) is that after ~15 min idle 'a walked-away session on a shared machine can't be resumed.' The idle callback runs wipeWebSecureState(), which deletes tokens + the IndexedDB snapshot + the AES key. But the TODO at session.web.ts:169-175 concedes it does NOT flip the React SessionContext to logged-out and does NOT clear the in-memory sql.js Database (schema.web.ts 'raw' is never closed/nulled on wipe). So a person who walks up to the idle, unlocked browser still sees every screen fully populated and can read/search all inventory, users, jobs, and locations locally with no re-auth (offline-first reads hit the in-memory DB, not the server); only the next token-requiring network action bounces them. Worse, because writes call scheduleSave()->flush()->saveDbSnapshot()->getOrCreateSnapshotKey() (schema.web.ts:24-29, webCrypto.ts:112-134), any post-wipe write or the visibilitychange/pagehide flush hook (schema.web.ts:83-89) mints a FRESH AES key back into sessionStorage and re-writes a fully decryptable snapshot to IndexedDB, undoing the wipe's 'nothing decryptable at rest' guarantee while the tab stays open.

Fix

Drive the actual logout from the idle callback (call the SessionContext logout() as the TODO notes), and on wipe also close()/null the sql.js database and set persistenceDisabled or a wiped flag so flush()/getOrCreateSnapshotKey() cannot silently re-persist and re-key after a wipe. Navigating/reloading to the login route on idle would clear the JS heap copy of the DB as well.

MEDIUM #11 idor-mass-assignment

Media sync-write path bypasses the entity_type allowlist and URL validation the POST /media route enforces

apps/api/src/lib/syncPolicy.ts:207
Exploit

The real client creates media rows through the generic sync outbox, not routes/media.ts (media.ts:280-283 states this explicitly). For table 'media' the sync path applies only applyWritePolicy (syncPolicy.ts:146-188), which forces uploaded_by=caller but keeps entity_type, entity_id, url and thumbnail_url exactly as the client sent them (they are real columns, not in SENSITIVE_DENY, and there is no MEDIA_ENTITY_TYPES/KEY_RE check anywhere in sync.ts). The POST /media route guards both of these: media.ts:10 restricts entity_type to an operational allowlist because attaching media to users/teams/role_settings/app_config 'was an IDOR sink' (media.ts:8-9), and media.ts:147-166 binds url/thumbnail_url to a server-generated key to stop an 'SSRF/DB-pollution sink' where a client 'could point url anywhere and we'd store + serve it as this entity's media'. A user holding upload_media (a broad, team-grantable permission per TEAM_OVERRIDABLE_PERMISSIONS) pushes a media outbox INSERT with entity_type='users'/'app_config'/'teams', an arbitrary entity_id, and url='https://attacker.example/x.jpg'. The row is accepted (OPERATION_PERM.media INSERT='upload_media' at syncPolicy.ts:207) and, because media is in FULL_TABLES but not SCOPED_TABLES (sync.ts:75,105), is then pulled to every device and rendered by MediaGallery as that entity's media — re-opening exactly the IDOR (media on admin entities) and stored-arbitrary-content (client-controlled external URL shown in-app) sinks the POST route closes.

Fix

Enforce the same MEDIA_ENTITY_TYPES membership check and the KEY_RE + entity-prefix binding on url/thumbnail_url in the sync write path for table 'media' (reject the outbox entry otherwise), so the generic path has parity with routes/media.ts. Reuse the constants from media.ts rather than duplicating them.

LOW #12 credential-lifetime

Enrollment codes never expire — indefinitely valid until a PIN is set

apps/api/src/routes/users.ts:38
Exploit

issueEnrollmentCode (line 38) stores only a bcrypt hash of the 6-digit code with no issued-at/expiry column, and /auth/set-pin (auth.ts) validates the code with no time check. A code emailed at account creation (sendEnrollmentCodeEmail) or reissued via reset-enrollment-code stays valid forever until the user completes first-login. An intercepted email, a shoulder-surfed/forwarded code, or a code left in an inbox for months can still be replayed to set the victim's first PIN and seize the un-onboarded account. The set-pin per-user lockout throttles brute force but does nothing to bound the validity window of a known/leaked code. The reset-enrollment-code comment even refers to codes that were 'lost/expired,' but no expiry is actually implemented.

Fix

Add an enrollment_code_expires_at (e.g. NOW() + 24-72h) set at issuance/reissue and reject expired codes in /auth/set-pin; force admins to reissue after expiry. This also shrinks the exposure window of the reset-enrollment-code takeover above.

LOW #13 mass-assignment

media rows written via the sync outbox bypass the url/entity_type validation enforced by routes/media.ts

apps/api/src/routes/media.ts:150
Exploit

The dedicated POST /media route strictly validates entity_type against MEDIA_ENTITY_TYPES and the object key against KEY_RE anchored to entity_type/entity_id (media.ts:144-166), to prevent forged/foreign object URLs and attaching media to admin entities. But 'media' is also in ALLOWED_TABLES with op-perm upload_media (syncPolicy.ts:207) and no SENSITIVE_DENY entry, so a caller with upload_media can INSERT a media row through /sync/push with an arbitrary url, thumbnail_url, entity_type and entity_id (only uploaded_by is attribution-forced). The media table is a fully-synced, unscoped table, so the forged url is pulled to every device. This is explicitly acknowledged in media.ts:280-290 ('The real client creates media rows via the sync outbox (not this route), which does not validate url/thumbnail_url'), so it appears to be a deliberately accepted tradeoff for the delete-safety logic -- but it means the KEY_RE/entity allowlist hardening in the REST path is advisory-only, and a client can store arbitrary url strings (cross-entity object references or external URLs) that other clients render.

Fix

If the REST-path url/key/entity validation is meant to be a security boundary, mirror it in the sync write path (validate media.url/thumbnail_url with KEY_RE anchored to the row's entity, and reject entity_type not in MEDIA_ENTITY_TYPES) inside applyEntry or via a table-specific guard; otherwise document the accepted risk explicitly in syncPolicy for the media table.

LOW #14 access-control

Prod MinIO bucket set to whole-bucket anonymous download — all media world-readable, protected only by unguessable object keys

infra/docker-compose.prod.yml:65
Exploit

minio-init runs `mc anonymous set download local/${MINIO_BUCKET}` on the ENTIRE bucket (dev compose scopes this to just /thumbnails). Every uploaded object — full-resolution photos/videos attached to items, jobs, repairs, locations, and activity_log — is anonymously downloadable with no auth via s3.<domain>/<bucket>/<key>. Confidentiality rests entirely on the object key being unguessable (entity_type/<entity_id>/<uuid>.<ext>, two UUIDs, so effectively an unguessable capability URL). Impact is bounded because keys are not enumerable, but any leak of a media URL (via logs, push-notification payloads, shared screenshots, or a browser referer) grants permanent unauthenticated access to that object, and there is no way to revoke it short of deleting the object. This appears to be a deliberate capability-URL design (PUBLIC_MEDIA_URL serves media directly, no signed GET), but the widening from thumbnails-only (dev) to the whole bucket (prod) is worth an explicit decision.

Fix

If media is meant to be private, drop the anonymous policy and serve GETs via short-lived presigned URLs (the code already has an S3 signer). If public-by-capability-URL is intended, document the tradeoff and ensure media URLs are never emitted to lower-trust sinks (logs/notifications) than the media itself warrants.

LOW #15 client-hardening/inconsistent-threat-model

JWT and user_id persisted as plaintext in IndexedDB undermine the at-rest DB encryption against the same local-disk attacker

apps/mobile/src/auth/session.web.ts:68
Exploit

session.web.ts:12-18 documents that the refresh token is deliberately kept only in memory because 'anything written [to IndexedDB] sits on disk in plaintext and readable by anyone with local file access.' Yet saveSession() writes the JWT (idbSet(JWT_KEY,jwt)) and user_id (idbSet(USER_ID_KEY)) to that very IndexedDB in plaintext (session.web.ts:68-77). The entire point of AES-GCM-encrypting the sql.js snapshot is to deny a local-file-access attacker the dataset — but the same attacker who cannot decrypt the snapshot can lift the plaintext JWT from IndexedDB and, if it is still within its 15-minute validity, call the authoritative API (e.g. /sync/full, which per the hardening notes now requires auth but accepts a valid JWT) as that user and re-download the full dataset, plus learn the user_id. The co-located plaintext token partially defeats the snapshot encryption for the threat it targets.

Fix

Treat the JWT as sensitive at rest too: hold it in memory like the refresh token, or encrypt it with the same session key, accepting that a reload forces re-auth (consistent with the D4 refresh-token decision). At minimum, narrow the comment's claim so it does not imply on-disk state is protected when a live JWT sits beside it.

LOW #16 notification-abuse

Assignment notification lets any edit_inventory user push notifications to arbitrary users with no dedup or rate limit

apps/api/src/routes/sync.ts:311
Exploit

On a repairs UPDATE where assignee_id changed, sync.ts:311-321 calls deliver() to resolveRecipients('assignment', {userId: assignee}); the 'assignment' intrinsic recipient is simply [ctx.userId] (notifications.ts:95), i.e. whatever user id the caller put in assignee_id — with no requirement that the assignee is on the caller's team. There is deliberately no dedup key (sync.ts:309-310) and this path has no rate limit. A user with edit_inventory (repairs UPDATE perm, syncPolicy.ts:203) repeatedly toggles a single repair's assignee_id between arbitrary target user ids, generating an unbounded stream of inbox rows + Expo push sends to those users. Content is the fixed string 'You have been assigned a repair.', so this is annoyance / push-quota abuse rather than content injection, but it does let one low-privileged user notify any arbitrary user id on demand.

Fix

Rate-limit the assignment notification per caller (as /push/test and /broadcast already are via overRateLimit), and/or restrict assignment notifications to assignees who share a team with the caller so the path can't be used to ping arbitrary user ids.

So any authenticated user (even a read-only tier) or anyone who decompiles/steals an APK+local DB extracts the org signing secret and can mint valid INVS:<type>:<value>:<sig> tags for any item/value, defeating the QR signing control entirely.   • activity_log write path allows audit forgery and silent log-suppression. routes/sync.ts (~lines 137-166) forces user_id=caller but accepts client-supplied id, created_at, team_id, entity_id, note, metadata, job_id, latitude/longitude/location_accuracy. Two concrete abuses: (a) a user fabricates their own immutable audit entries with false GPS 'proof of presence', backdated created_at, and bogus metadata; (b) because the insert is `WHERE NOT EXISTS (SELECT 1 FROM activity_log WHERE id=$1)`, a malicious client can pre-insert a row with a chosen id so a future legitimate event carrying that id is silently dropped — audit suppression of a compliance-grade, Postgres-immutable (no-update/no-delete) log.
